# ADR-0006: Formatting with CSharpier

- **Status:** Accepted
- **Date:** 2026-09-28 (ported from the Java set's "Spotless and palantir-java-format", 2026-08-26)
- **Deciders:** Martin

## Context

Unformatted code is affordable only until two people, or a person and an AI tool, touch
the same file. After that, reformatting noise hides the actual change in review, and "fix
the formatting" becomes a review comment someone has to write over and over.

.NET offers two kinds of tool. `dotnet format` applies `.editorconfig` rules: it is
configurable, built into the SDK, and also fixes analyzer and code-style diagnostics.
[CSharpier](https://csharpier.com) is an opinionated formatter in the style of Prettier,
with almost no options. The Java set chose palantir-java-format for the same reason:
Java lacked a formatter like CSharpier.

## Decision

CSharpier formats all C# sources. It is installed as a local tool
(`.config/dotnet-tools.json`), so the version is pinned in the repository. CI runs
`dotnet csharpier check .` and fails on any difference. `dotnet csharpier format .`
reformats the repository.

`dotnet format` stays, restricted to what CSharpier does not do: analyzers and code style
(`dotnet format analyzers --verify-no-changes`, `dotnet format style --verify-no-changes`).
Its whitespace formatting is never run. `.editorconfig` keeps the rules for naming,
`var` usage and analyzer severities, and leaves layout to CSharpier.

CSharpier's defaults are used as they are, with no `.csharpierrc`.

## Alternatives considered

- **`dotnet format` alone, driven by `.editorconfig`**: no extra tool, and project-specific
  rules. Rejected: every rule it exposes is an invitation to discuss it, which is the
  discussion a formatter exists to end. It also leaves much of the layout (line breaking,
  argument wrapping) to whoever wrote the code.
- **Both formatters on whitespace**: rejected outright. Where they disagree, each one
  undoes the other and CI fails in turns.
- **Formatting on save in the IDE only**: no CI change. Rejected: it enforces nothing for
  a contributor whose IDE is set up differently, and nothing at all for code generated by
  a tool.

## Consequences

- Formatting stops being reviewable, and therefore stops being reviewed. This is the point.
- The first `csharpier format` touches nearly every file. It is committed on its own, so
  it can be skipped with `git blame --ignore-rev` and does not obscure any real change.
- A build can now fail for a reason that has nothing to do with correctness. The fix is
  always one command, and the Rider or Visual Studio plugin keeps it from happening.
- For an AI agent, this is one more command in its local checks: `dotnet csharpier format .`
  before committing. Leaving it out is the most likely first CI failure, so the
  repository's `AGENT.md` must list it with the other checks.
- This differs from the AaaS golden-path template, which uses `dotnet format` for
  everything. A template adopting these guidelines changes its CI accordingly.
